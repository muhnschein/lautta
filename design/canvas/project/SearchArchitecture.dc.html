How search finds things

Issue 43 · architecture options for device and server locations through netvfs. Estimates are marked as such: not measured yet.

Three ways to answer a search

1 · Walk every time

Today's search, made better

  • Lists folder after folder, locations in parallel; results stream in
  • Always current; nothing stored
  • Device: fine (seconds). Server: one listing per folder, every search: 10 000 folders ≈ 30 s on LAN, ≈ 5 min over the internet (estimate)
  • Offline server: nothing
  • netvfs: nothing new (bridge Walk exists)

2 · Reuse what was seen

Listing cache as a free index

  • Lautta already keeps listings (7 days, per location opt-out): search them first, instantly
  • Then walk live, as in 1, to add and drop hits
  • Finds only folders you or earlier searches opened
  • Offline server: what was seen, marked with its age
  • netvfs: nothing new

3 · Own name index recommended

2 plus a full crawl you switch on per location

  • SQLite table of names (path, kind, size, date) in lautta.db; no contents
  • Device and SD: on by default, kept fresh while Lautta is open (folder dates show what changed)
  • Servers: opt-in per location, crawl runs as an activity you can pause
  • Search = index at once, then live check of the hits and of folders that changed
  • netvfs: nothing new to start; two small additions make refreshing cheap (below)

One search, step by step (option 3)

netvfs API: what this would need

netvfs#48 is weighing a stable org.netvfs.Bridge1. Options 1 to 3 run on today's calls (List, Walk, WalkBatch, entry etag). Three additions, each optional, each additive behind a feature word so old clients are unaffected:

a · Capability word "deep-etag" in Capabilities(loc): folder etag covers its whole subtree (Nextcloud, ownCloud). Lets Lautta skip unchanged branches. Tiny; fits the stable set.
b · Walk option "skip": folder paths with their last etag; bridge doesn't descend where the etag still matches. Saves the app-to-bridge round trips of doing the same with List. Small; worth it only with a.
c · New method Search(loc, root, query, opts) → job, hits as WalkBatch, feature word "search": WebDAV SEARCH first. New surface with its own query format: keep it out of the first stable set and mark it experimental.

Not proposed: indexing inside netvfs (its spec rules out caches and UI), Tracker (needs Media index permission, covers only media folders, missing on our test phones), searching file contents.
